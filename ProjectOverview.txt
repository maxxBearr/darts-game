# Dart Roguelike — Project Knowledge & Phase Outline

---

## Game Concept

A **Balatro-style roguelike** built around darts. The player customizes a dart across four components — **point, barrel, shaft, and flight** — with each part affecting throw stats. Runs scale through an **x01 format** (101 → 201 → 301 → etc.), with escalating score targets requiring increasingly powerful builds to keep pace.

### Core Pillars

- **Throw Mechanic:** A three-stage input system (aim → vertical window → release) that blends deliberate positioning with timing-based skill. Build stats directly affect each stage's difficulty and precision.
- **Build System:** Mario Kart-style stat spreads across dart components. An Armored Core-inspired **balance threshold** prevents pure stat stacking and forces meaningful tradeoffs.
- **Modifiers/Items:** Roguelike items that change how the player sees and values the dartboard — e.g., triples worth more but doubles worth 0, odd numbers doubled, red zones give bonus points. The board is always the same, but the build makes you play it differently every run.
- **Form (Deck Equivalent):** The player's throwing style, chosen at the start of a run. Changes the fundamental feel of the throw mechanic — e.g., different meter behavior, snap-to-wedge aiming, bonus streaks. Analogous to Balatro's deck choice.

### Win Condition / Progression

- Scaling x01: Round 1 is 101 in ~9 darts. Each subsequent round adds 100 (201, 301, 401...).
- The classic 501 becomes a mid-run challenge; later rounds (701, 801+) require strong builds.
- Dart count per round is another potential difficulty lever (could vary by stage or modifier).

### Stat Categories

| Stat | What It Affects | Throw Stage |
|------|----------------|-------------|
| Aim Accuracy | Horizontal line thickness (variance band) | Stage 1 — Aim |
| Vertical Accuracy | How much the vertical window shrinks | Stage 2 — Window |
| Release Speed | How fast the bounce marker moves (timing difficulty) | Stage 3 — Release |
| Release Accuracy | Vertical variance zone around the marker on release | Stage 3 — Release |
| Balance | Global threshold — need minimum to function (Armored Core weight) | All stages |
| Weight | Affects other stats, interacts with balance | TBD |

### Dart Components → Stats (Tentative)

| Component | Primary Stats |
|-----------|--------------|
| Flight | Aim accuracy (horizontal control) |
| Point | Release accuracy (vertical precision) |
| Barrel | Release speed (bounce timing difficulty), weight |
| Shaft | Balance, vertical accuracy |

## Current Codebase — What Exists

### Tech Stack
- **Engine:** Godot 4
- **Language:** GDScript
- **Scripts location:** `res://scripts/`

### Scene Tree

```
Main (Node2D) — main.gd
├── Dartboard (Node2D) — dartboard.gd
├── ThrowMechanic (Node2D) — throw_mechanic.gd
├── DartContainer (Node2D) — holds dart marker instances
└── HUD (CanvasLayer) — hud.gd

    ├── ThrowAgainButton (Button)
    ├── ClearButton (Button)
    └── InstructionLabel (Label)
```

### File Descriptions

**`dartboard.gd`** — Procedurally drawn dartboard with polar-coordinate scoring.
- Draws all segments using `_draw()` with concentric rings and 20 angular wedges.
- All ring radius thresholds are normalized constants (0.0–1.0), multiplied by `board_radius` at draw/score time.
- Standard dartboard number order: `[20, 1, 18, 4, 13, 6, 10, 15, 2, 17, 3, 19, 7, 16, 8, 11, 14, 9, 12, 5]`
- `calculate_score(global_hit_position)` converts a pixel position to angle + distance, returns a dictionary with `face_value`, `multiplier`, `total_score`, `ring_name`.
- All colors are exported and tweakable.
- Ring thresholds: Double Bull 0–0.032, Single Bull 0.032–0.08, Inner Single 0.08–0.48, Triple 0.48–0.53, Outer Single 0.53–0.76, Double 0.76–0.83, Off Board 0.83+.

**`throw_mechanic.gd`** — Three-stage throw input system.
- `ThrowState` enum: `IDLE, AIMING, POSITIONING, RELEASING, DONE`
- **AIMING:** Vertical highlight band follows mouse horizontally. Width = `aim_accuracy * 2`. Click/Space to lock.
- **POSITIONING:** Locked band shrinks via tween to a shorter window based on `vertical_accuracy`. Player moves window with W/S or Up/Down arrows. Enter/Space to lock.
- **RELEASING:** Bounce marker moves within the locked window via sine wave. Speed based on `release_speed`. Click/Space to release.
- **DONE:** Dart resolves — horizontal offset from `aim_accuracy`, vertical offset from `release_accuracy`, both using `randf_range`.
- Signals: `throw_completed(hit_position)`, `state_changed(new_state)`.
- Key exported stats: `aim_accuracy` (30.0), `vertical_accuracy` (0.5), `release_speed` (3.0), `release_accuracy` (20.0).

**`main.gd`** — Scene controller and game flow orchestrator.
- Centers dartboard on screen.
- Connects signals between throw mechanic, HUD, and scoring.
- `_place_dart()` creates dart marker instances at landing positions.
- Tracks running `_total_score`.
- Updates HUD instructions based on throw state.

**`hud.gd`** — HUD overlay with score display and controls.
- Shows current throw result (ring name, points).
- Shows running total score.
- Instruction text updates per throw stage.
- Throw Again and Clear Board buttons (hidden during active throw).

**`dart_marker.gd`** — Visual marker for landed darts.
- Simple drawn circle with outer ring and dark inner center.
- Color and size set by `main.gd` when instantiated.

## Coding Conventions

- **Static typing on ALL variables** — no exceptions.
- **Frequent commenting** — every function, every logic block, non-obvious lines.
- **`##` doc comments on all `@export` vars** — describe what it does, what values mean, how it affects gameplay.
- **`@export` liberally** — any tunable value (colors, speeds, thresholds, sizes, durations) should be exported for inspector tweaking.

## Phase Outline

### Phase 1 — Dartboard & Basic Throw ✅ COMPLETE

**Goal:** Prove the core loop — throw darts at a working dartboard with accurate scoring.

**What was built:**
- Procedurally drawn dartboard with all segments, wires, and bullseyes.
- Polar coordinate scoring system (angle → wedge, distance → ring → multiplier).
- Two-stage throw: aim line (horizontal drag + lock) → release marker (bouncing + tap).
- Dart markers placed on board at landing positions.
- HUD with score display, running total, throw again / clear buttons.
- All values exported with descriptions.

---

### Phase 2 — Vertical Window Stage ✅ COMPLETE

**Goal:** Add the vertical window positioning stage between aim and release for more player control and a natural home for the `vertical_accuracy` stat.

**What was built:**
- New `POSITIONING` state in the throw flow.
- After aim lock, the line visibly shrinks (tweened) based on `vertical_accuracy`.
- Player repositions the shortened window with W/S or Up/Down.
- Enter/Space locks the window; release marker bounces within window bounds only.
- Window clamped to board bounds, visually distinct from dimmed aim band.

---

### Phase 2.5 — Resolve Preview ⬜ NEXT UP

**Goal:** Add a brief visual pause between clicking the release and the dart landing, showing the player the full landing zone before the dart resolves.

**What to build:**
- New `RESOLVING` state between RELEASING and DONE.
- On release click, marker freezes and the glow zone expands to show the full variance rectangle (aim accuracy width × release accuracy height, centered on frozen marker, clamped to window).
- Brief pause (`resolve_preview_duration`, ~0.5s) before dart resolves.
- Gives the player visual feedback on how their release accuracy stat affects outcomes.

**Spec:** Small enough to paste directly into Claude Code as instructions (see chat history for the exact text).

**Ideas collected so far:**

---

### Phase 7 — Form System ⬜ PLANNED

**Goal:** Implement the "deck" equivalent — different throwing forms that change the fundamental feel.

**Ideas collected so far:**
- Precision form: tight aim, narrow release window.
- Lob form: wide forgiving release, more aim drift.
- Speed throw: faster meters, bonus for consecutive accuracy.
- Different meter behaviors (sine wave vs linear, snap-to-wedge, etc.).

## Design Questions Still Open

1. **501 checkout rules:** Should the player have to finish on a double (standard darts rule), or is that too punishing for a roguelike? Could be a modifier/item instead.
2. **Dart count scaling:** Fixed per round? Decreasing as difficulty climbs? Modifier-dependent?
3. **Balance threshold specifics:** What happens when you exceed it? Stat penalties? Locked out of throwing? Visual warning?
4. **Modifier stacking:** Can modifiers conflict (e.g., "doubles worth 0" + "must finish on a double")? Is that a design feature (risk/reward) or something to prevent?
5. **Distribution type for variance:** Currently using uniform `randf_range`. Gaussian would feel more natural (most darts near center, fewer at edges). Worth implementing?
